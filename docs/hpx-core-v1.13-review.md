## 3. コメントの誤り (動作には影響なし)
- 169行目「16バイト×2400=約38KB」→ 記録は20バイトなので約48KB。
- 735行目「16バイトの記録を追記」→ 20バイト。
- 740行目「スロット番号 0〜3」→ 0〜7 (最大8台)。
- 284〜285行目 BleRec の `bat`「電池残量 [%]」、`flags`「bit0/bit1」: 重量・電柵では電圧 ((mV-2000)/10)、bit2 (重量)・bit3 (電柵) もある。
- 715〜721行目 「ここに重量・電柵などを足す」→ もう BLE 経由で実装済み。

## 4. 重複 (まとめると短くなる箇所)
- **電池電圧の文字列化** `String(2.0f + r.bat * 0.01f, 2)` が 1560・1568・2552・2561・2609行目の5か所。関数1つにまとめられます。
- **`bleParseW()` と `bleParseA()`** (970〜1015行目): リトルエンディアンの読み出しと、電池 mV → `bat` の換算が同じ。`le16()` と `bleSetBattMv()` のような小関数にまとめられます。
- **`postJson()`** (1699〜1731行目): https と http で、ヘッダー追加と POST の部分が丸ごと同じ。クライアントだけ分けて、残りを共通にできます。
- **センサ種類の表示名** (`kind == 1 ? 重量センサ : kind == 2 ? 電柵アラート`) と、`flags` による分岐 (重量 / 電柵 / 温湿度) が、JSON・記録画面・CSV・状態表示の4か所でそれぞれ書かれています。
- **`handleUpdateFinish()`** (2858〜2863行目) は `pageHead()` と同じ HTML の頭を自前で書いています (refresh の meta を足すためだけ)。

## 5. 確認して問題なかったところ
- 記録ファイルの整理・電源断からの回復、送信済みの印 (`sent`) と分割送信、削除済みセンサの記録の読み飛ばし
- 時計の区切りへの合わせ方 (`bleDue` / `bleRecordTs` / `secToNextBoundary`)
- 重量センサの「測定停止」(spread=0xFFFF) はサーバーの receive.php 側でも扱われている
- OTA (アップロード・HTTPS・ロールバック)、WDT、ループ内の millis の扱い
